시장/기술 동향 분석

1. 시장 동향

  • AI 학습 데이터 시장은 2024년 약 26억 달러에서 2030년 86억 달러로 연평균 21.9% 성장 전망 (Grand View Research, 2025)
  • 생성형 AI·LLM 확산으로 출처와 품질이 확인된 학습·분석용 데이터 수요 증가
  • 국내 공공데이터는 OECD 공공데이터 평가(OURdata Index)에서 4회 연속 1위 기록, 개방 건수는 꾸준히 증가
  • 개방은 원천 API 제공까지이고, 분석·학습에 바로 쓸 수 있는 표 형태로 가공하는 작업은 이용자 몫으로 남아 있음
  • → 공공데이터를 수집·정제·검증해 재사용 가능한 테이블과 데이터셋으로 만들어 주는 도구가 필요한 시점

구성 요소역할

kpubdata공공 API 접근 라이브러리. 제공 기관별 호출과 표준 레코드 변환 담당
저장소실행 작업공간(로컬 파일), 웨어하우스 스냅샷(Parquet), SQLite 인덱스
외부 대상Hugging Face·Kaggle 등 게시 대상, OIDC 인증 제공자(Keycloak)

2. 테이블 만들기 (Studio 기반)

  • ① 사용자가 Studio 카탈로그에서 소스를 고르고 규칙(BuildSpec)을 구성
  • ② Studio가 Builder API에 미리보기와 검증을 요청해 스키마와 샘플 확인
  • ③ 만들기를 실행하면 Builder가 Bronze→Silver→Gold로 가공하고 스냅샷과 Manifest 생성
  • ④ 사용자는 테이블 상세, SQL 작업 공간, 리포트에서 결과 활용

3. 정기 수집·게시 (일정 기반)

  • ① GitHub Actions 일정이 분야별 수집 작업을 주기적으로 시작 (기상 3시간, 관광·의약품 주 1회, 부동산 월초)
  • ② kpubdata가 공공 API에서 데이터를 수집하고 게시 스크립트가 정제·패키징
  • ③ 검증을 통과한 데이터셋을 Hugging Face에 게시
  • ④ 실패하면 이슈를 자동 등록해 담당자가 확인
  • 정기 게시는 기존 게시 스크립트 경로로 동작하며, BuildSpec 기반 경로로 순차 이전 중임

엔티티 관계도 - 핵심 도메인 모델

  • BuildSpec은 실행 입력을 선언하는 계약이며 Python dataclass로 정의함
  • BuildManifest는 실행마다 한 건씩 남는 결과 기록임
  • 관계형 스키마가 아니므로 UML 클래스 다이어그램 표기법으로 정리함

엔티티 관계도 - 저장 구조 (ERD)

  • 상태는 SQLite와 로컬 파일에만 보관함
  • builds는 manifest.json과 종료 기록에서 다시 만들 수 있는 파생 인덱스임
  • tables·table_snapshots는 웨어하우스 카탈로그이며 스냅샷 본문은 Parquet 파일임
  • 주요 컬럼만 표시함

기능 처리도 - 테이블 만들기

  • 사용자 조작(①⑦)은 Studio 안에서 처리되고, Builder API 호출은 미리보기·검증·존재 확인·제출 네 곳임
  • 미리보기와 검증은 동시에 요청하며, 늦게 도착한 이전 응답은 버림
  • 제출 직전에 같은 이름의 테이블이 있는지 다시 확인하고, 결과가 달라졌으면 제출하지 않음
  • 마법사는 완료를 기다리지 않고 실행 상세로 넘어가며, 진행은 실행 상세가 따라감

기능 처리도 - 실행 검토·재실행

  • 실행 상세는 단계·품질·이벤트·명세를 따로 조회해 한 영역의 실패가 전체를 막지 않게 함
  • 실패하거나 취소된 실행을 다시 돌릴 때만 retry_of를 보내며, 수집 체크포인트를 이어받음
  • 성공한 실행을 다시 돌리는 것은 갱신이며 새 스냅샷을 만듦

기능 처리도 - 게시

  • 게시 전 준비 상태를 조회해 라이선스, 개인정보 검사, 카드 누락 등 차단 사유를 먼저 표시
  • Studio의 게시 대상은 Hugging Face이며, Builder CLI는 로컬·Kaggle 게시도 지원
  • 게시 요청은 자동 재시도하지 않으며, 결과가 불명확하면 대조 또는 영수증 초기화로 복구

기능 처리도 - 오류 처리

  • ① 명세 검증 오류 — 문제 목록을 표시하고 수정 전까지 실행을 막음
  • ② 연결 실패 — 30초 제한과 최대 2회 재시도 후 오류 상태와 다시 시도 버튼 표시. 미리보기·제출·게시·쿼리는 재시도하지 않음
  • ③ 인증 만료 — 토큰을 갱신해 같은 요청을 한 번 다시 보내고, 실패하면 로그인 화면으로 이동
  • ④ 실행 실패 — 실행 상세에서 실패 단계와 코드를 확인하고 명세를 고쳐 재실행
  • 오프라인 모드나 자동 재연결은 두지 않음. 주기적 조회가 돌아오면 화면이 갱신됨

기능 처리도 - Ask KPubData 응답 처리

  • 프롬프트 역할 분리: 고정 지시(system), 신뢰하지 않는 근거(evidence), 사용자 질문을 구분해 전달
  • 전송 전 비밀값 제거: 키·토큰 이름의 필드, key=value 형태, 무작위성이 높은 긴 문자열을 자리표시자로 치환
  • 4단계 검증: ① Zod 구조 검증 → ② 근거 대조 → ③ Builder 검증 → ④ 사용자 승인
  • SQL 안전성 검사는 Studio가 아니라 Builder의 읽기 전용 검사가 담당
  • 허용 동작 6종: OPEN_PROVIDER, OPEN_BUILD, OPEN_QUALITY, PATCH_BUILDSPEC, CREATE_BUILD_DRAFT, ADD_REPORT_BLOCK
  • 실행 시작, 게시, 자격 증명 변경, SQL 자동 실행은 제안할 수 없음
  • LLM 키는 사용자가 직접 입력(BYOK)하며 기본적으로 메모리에만 보관

알고리즘 명세서

  • ① run_build()가 BuildSpec을 받아 validate_spec()으로 먼저 검증. 위반이 있으면 ValidationError로 끝나며 작업공간도 기록도 만들지 않음
  • ② BuildContext.create()로 실행 작업공간을 만들고 명세 스냅샷(buildspec.yaml)과 spec_digest 기록
  • ③ 소스를 스레드 풀로 병렬 실행 (최대 4개). 결과는 명세에 적힌 순서대로 모음
  • ④ 소스마다 Bronze → Silver → Gold → Export 순으로 진행. 단계 경계마다 취소 여부 확인
  • ⑤ Silver에서 스키마 검증, 개인정보 검사, 품질 검사를 통과해야 Gold로 넘어감
  • ⑥ composition을 선언했으면 두 소스의 Silver를 조인해 하나의 Gold 생성
  • ⑦ 상태 판정: 취소되었으면 cancelled, 오류가 하나라도 있으면 failed, 아니면 ok
  • ⑧ 상태가 ok일 때만 Gold를 웨어하우스 스냅샷으로 커밋. 시작 시점의 revision과 비교해 충돌하면 거부
  • ⑨ manifest.json을 기록하고 BuildResult(status, outcomes, manifest_path, …) 반환

알고리즘 명세서 - 웨어하우스 커밋

○ 상태가 ok인 실행의 Gold를 읽기 전용 스냅샷으로 커밋하고 테이블의 현재 스냅샷을 바꿈

  • 스냅샷은 임시 위치에 쓴 뒤 검증을 거쳐 tables/{id}/snapshots/{id}/로 옮기고 읽기 전용으로 만듦
  • 테이블마다 revision을 두고, 커밋할 때 revision을 하나 올림
  • 이전 스냅샷은 최근 3개까지 보관하고 나머지는 정리. 저장된 분석이 붙잡고 있는 스냅샷은 정리하지 않음

커밋 거부 사유

사유 코드발생 조건처리
table_exists새 테이블로 만들기를 요청했는데 같은 이름의 테이블이 이미 있음커밋하지 않고 실패로 기록

  • 커밋을 Manifest 기록보다 먼저 수행해, 커밋 실패가 Manifest와 인덱스에 남도록 함

알고리즘 명세서 - 읽기 전용 SQL 검사와 비밀값 제거

읽기 전용 SQL 검사 (Builder)

  • 입력은 비어 있지 않고 64KiB 이하
  • sqlglot으로 DuckDB 문법 분석. 구문 오류는 거부
  • 문장은 정확히 하나, SELECT·CTE·집합 연산만 허용 (DDL·DML 불가)
  • 재귀 CTE 불가, dataset이라는 이름의 CTE 불가
  • VALUES, UNNEST, LATERAL, 테이블 함수, 표본 추출(TABLESAMPLE) 불가
  • 환경을 들여다보는 함수(current_setting, getenv, version 등 44종) 불가
  • 결과가 매번 달라지는 함수(random, uuid, now 등 18종) 불가
  • 실제 테이블 참조는 따옴표·스키마 지정 없이 dataset 하나만 허용
  • 검사를 통과한 문장은 주석을 뺀 표준형으로 다시 만들어 실행하며, 원문은 DuckDB에 전달하지 않음
  • 검사는 3중 방어의 첫 단계. 그 뒤에 잠긴 DuckDB 연결과 별도 자식 프로세스가 있음

LLM 전송 전 비밀값 제거 (Studio)

  • 필드 이름이 키·토큰·시크릿을 뜻하면 값 제거 (servicekey, api_key, *token, *secret)
  • 본문 속 key: value, key=value 형태 제거
  • 24자 이상이고 무작위성(섀넌 엔트로피 4.0비트/문자 이상)이 높은 문자열 제거
  • 제거한 값은 자리표시자로 바꾸고 응답을 받은 뒤 브라우저에서만 되돌림
  • Builder가 확인해 준 실행 ID와 근거 ID는 제거 대상에서 제외

배포

  • Builder: Docker 이미지로 HTTP 서비스 실행. 산출물과 상태는 /data 볼륨에 보관
  • 인증 없이 띄울 수 없음 (API 키 또는 OIDC 필수). 개발 모드에서만 인증 생략 가능
  • 설정은 환경변수로 주입: 인증·접근, 제공 기관 키, 실행·동시성, 업로드·URL 소스, 상태 저장·웨어하우스, 게시
  • 기동할 때 설정을 검사하고, settings 명령으로 실제 적용 값을 확인
  • 제공 기관 자격 증명은 마스터 키로 암호화해 저장
  • Studio: 정적 빌드를 nginx 이미지로 제공. Builder 주소와 OIDC 설정은 컨테이너를 띄울 때 주입 (/config.js)
  • 데모 모드: Builder 없이 고정 데이터로 동작하며 모든 화면에 Demo 배지 표시
