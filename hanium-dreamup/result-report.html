Ⅰ. 프로젝트 개요

1. 프로젝트 소개

1) 프로젝트 정의

  • 공공데이터를 분석 가능한 테이블로 가공하고 그 과정을 추적·확인하는 플랫폼
  • 사용자가 선언한 규칙에 따라 수집, 정제, 검증, 패키징, 기록을 자동 수행
  • 생성된 테이블은 스냅샷으로 보관하여 SQL 분석, 리포트, 내보내기, 게시에 활용
  • 기획 의도: 공공데이터의 '수집'과 '활용 가능한 형태로의 가공' 사이의 간극 해소

2) 구성 요소

구성 요소형태역할
KPubData BuilderPython 패키지, HTTP 서비스, CLI명세 검증, Bronze·Silver·Gold 실행, 테이블 스냅샷과 Manifest 기록, 읽기 전용 SQL, 내보내기와 게시
KPubData StudioReact 웹 애플리케이션카탈로그 탐색, 테이블 만들기, 테이블 조회, SQL 분석, 리포트, 실행·품질·운영 확인
kpubdataPython 라이브러리제공 기관별 공공 API 호출 및 표준 레코드 변환. Builder에서 호출하여 사용
BuildSpecYAML·JSON 명세소스, 스키마 계약, 품질 기준, 분할, 내보내기를 선언하는 실행 입력
Manifestmanifest.json실행별 결과 기록: 상태, 출처, 행 수, 품질 결과, 실패 내역
웨어하우스Parquet 스냅샷 + SQLite 카탈로그성공한 실행 결과를 읽기 전용 스냅샷으로 보관

3) 사용 흐름

  • ① 카탈로그 내 소스 데이터셋 검색 후 '시작' 선택
  • ② 테이블 만들기 마법사에서 파라미터·규칙 입력
  • ③ 미리보기로 스키마·샘플 확인, 검증 통과 후 '만들기' 실행
  • ④ Builder의 수집~스냅샷 커밋 수행 중 실행 상세에서 진행 상황 확인
  • ⑤ 테이블 상세에서 스키마·품질 확인, SQL 작업 공간에서 분석, 리포트 작성
  • ⑥ 필요 시 파일 내보내기 또는 Hugging Face 게시

4) 주요 용어

용어뜻
소스 데이터셋제공 기관이 공개한 원천 데이터. 카탈로그에서 조회
테이블소스 데이터셋을 가공한 결과물. 스냅샷의 집합
스냅샷1회 실행으로 커밋된 읽기 전용 결과. 테이블별 최근 3개 보관
실행BuildSpec 1건을 처리하는 작업 단위. run_id로 식별
Bronze원천 레코드를 변형 없이 보존하는 단계
Silver선언한 규칙에 따라 정규화·검증하는 단계
Gold컬럼 선택·마스킹·분할을 적용한 최종 단계

2. 개발 배경 및 필요성

1) 공공데이터 활용 환경

  • 생성형 AI 확산에 따라 출처와 품질이 검증된 학습·분석용 데이터 수요 증가
  • AI 학습 데이터 시장은 2024년 약 26억 달러에서 2030년 86억 달러로 성장 전망 (Grand View Research, 2025)
  • 국내 공공데이터는 OECD 공공데이터 평가 4회 연속 1위. 개방 규모는 크나 가공은 이용자 부담

2) 기존 방식의 문제

구분문제
형식 차이기관별 응답 형식(XML·JSON), 페이지 처리, 인증 방식, 컬럼 명칭이 상이하여 소스별 수집 코드 개별 작성 필요
정제 반복결측 표기('-', 'N/A'), 숫자 내 쉼표, 코드 앞자리 0 누락 등을 매회 수작업으로 정리
이력 부재입력·규칙에 대한 기록 부재로 동일 결과 재현 곤란
품질 확인중복, 결측, 범위 이탈에 대한 배포 전 확인 절차 부재
법적 확인개인정보 포함 여부, 재배포 조건을 수작업으로 별도 확인
접근 장벽스크립트·명령줄 중심으로 비개발자의 접근 곤란

3) 개발 목표

  • 수집부터 배포까지의 규칙을 단일 명세로 선언하고 실행 전 검증
  • 단계별 결과를 파일로 보존하여 문제 발생 지점 확인 가능
  • 품질·개인정보·라이선스 점검을 실행 과정에 내재화
  • 동일 기능을 웹 화면에서 코드 작성 없이 제공
  • 결과 테이블을 스냅샷으로 보관하여 분석 재실행 시 동일 입력 보장

3. 프로젝트 특·장점

1) 기존 방식과의 비교

구분기존 방식본 프로젝트
공공데이터 포털원천 API 제공 중심. 가공은 이용자 부담정제·검증·분할·문서화를 거친 테이블·데이터셋 산출
범용 ETL 도구
(Airflow 등)		파이프라인 실행은 가능하나 검증 규칙은 직접 구현스키마 계약·품질 기준을 명세에 선언하고 실행 전 검증
데이터 허브
(Hugging Face 등)		배포·공유 중심. 생성 과정 미기록실행 기록·입력 지문을 Manifest로 기록하고 카드와 함께 게시
LLM 데이터 도구LLM이 내용을 추정하여 생성답변을 실제 근거와 대조하고 사용자 승인 후에만 실행

2) 기술적 차별점

  • 명세 기반 실행
    • BuildSpec을 실행의 단일 입력으로 사용. 화면에서 구성한 설정도 동일 명세로 변환하여 전달
    • 실행 전 15개 영역 검사, 문제를 code·path·message 형식으로 일괄 반환
    • 실행에 사용한 명세를 스냅샷으로 보존하여 동일 조건 재실행 가능
  • 단계별 결과 보존
    • Bronze·Silver·Gold 결과를 단계별 파일로 보존하여 개별 확인 가능
    • 일부 소스 실패 시에도 나머지 소스는 계속 처리, 실패 단계·코드 기록
  • 스냅샷과 재현성
    • 테이블은 읽기 전용 스냅샷으로 커밋. 저장한 분석은 조회 대상 스냅샷 정보와 함께 보관
    • 입력 지문, 분할 알고리즘, 산출물 다이제스트를 Manifest에 기록
  • 실행 과정에 내재화한 점검
    • 품질 검사 7종, 개인정보 패턴 검사와 마스킹, 재배포 조건 판정
    • 게시 전 준비 상태 점검: 라이선스, 개인정보 검사 통과, 카드 항목 누락
  • 역할 분리
    • Studio는 화면, Builder는 검증·실행·질의, kpubdata는 공공 API 접근
    • Studio는 Builder 미제공 값을 임의 생성하여 표시하지 않음 (점수 대신 검사 결과 표시, 미수신 값은 '확인 불가' 표기)
  • 근거 기반 AI 도우미
    • 답변의 참조·동작·SQL을 Builder 제공 근거와 대조
    • SQL 실행·명세 변경은 사용자 승인 후에만 수행

Ⅱ. 프로젝트 내용

1. 프로젝트 구성도

1) 시스템 구성도

  • Studio는 실행 기능 없이 Builder API만 호출
  • Builder는 kpubdata를 통해 원천을 수신하여 Bronze → Silver → Gold 순으로 처리
  • 성공한 실행의 Gold는 테이블 스냅샷으로 커밋, 실행 내역은 Manifest·SQLite 인덱스에 기록
  • SQL 질의는 저장된 스냅샷을 대상으로 읽기 전용 조회

2) 서비스 흐름도

  • 미리보기·검증은 저장 없이 수행. 검증 통과 후 실행 제출
  • 실행은 비동기 방식. Studio는 800ms 간격으로 상태 조회, 탭 비활성 시 조회 중단
  • 작업 상태: queued → running → succeeded · failed · cancelled

3) 데이터 처리 흐름

단계처리산출물
Bronze공공 API·업로드 파일·URL의 원본을 변형 없이 수집, 수집 시각·파라미터·건수·체크섬 기록raw_records.jsonl, metadata.json
Silver선언한 규칙에 따른 정규화, 스키마 검증, 개인정보·품질 검사, 통계·미리보기 생성table.parquet, schema.json, stats.json, validation.json
Gold행 필터와 컬럼 선택, 개인정보 컬럼 마스킹, 분할, 두 소스 조인table.parquet, package.json, splits/*.parquet
Export지정 형식으로 내보내기, 데이터셋 카드 생성CSV·JSONL·Parquet·Markdown 파일, README.md, card.json
커밋·기록상태가 ok인 경우 웨어하우스 스냅샷 커밋, Manifest 기록스냅샷, manifest.json

4) 저장 구조

  • 별도 DB 서버 없이 SQLite·로컬 파일로 구성
  • 실행 작업공간: {output}/{run_id}/ 아래에 bronze/, silver/, gold/, buildspec.yaml, manifest.json
  • 웨어하우스: {warehouse}/tables/{id}/snapshots/{id}/에 Parquet. 카탈로그는 _warehouse.sqlite
  • 실행 인덱스(_builds.sqlite)는 Manifest로부터 재구성 가능한 파생 자료
  • 실행 이벤트, 게시 영수증, 저장된 분석, 명세 개정 이력, 자격 증명(암호화)은 각각 별도 SQLite 파일로 보관

3. 주요 적용 기술

1) 선언형 실행 계약 (BuildSpec)

  • 필수 항목은 dataset_id, title, description, sources 4개. 그 외 항목은 필요 시 선언
  • 소스별 스키마 계약(schema)·Gold 선택(gold) 개별 지정
  • exports 생략 시 테이블 커밋까지 수행 (내보내기는 선택 사항)
명세 항목선언 내용
sources[]소스 종류(public_api·file·url), 제공 기관·데이터셋, 수집 파라미터, 스키마 계약, Gold 선택
quality중복률·결측률 상한, 최소 행 수, 값 범위, 컬럼 비교와 규칙별 심각도
pii개인정보 검사 정책 (block·warn·allow)
splits분할 방식(ratio·key), 비율, 시드
composition두 소스의 조인 정의 (키, inner·left, 중복·결측 키 처리)
exports[]내보내기 형식과 경로
license 등라이선스, 출처 표기, 게시 여부, 갱신 주기
  • 검증은 실행 자원 생성 전 수행, 문제 전체를 일괄 반환
  • 검사 영역: 필수 항목, 소스 식별, 내보내기, 메타데이터, 분할, 스키마 계약, 소스 종류, 소스 키, 파라미터 축, 개인정보 정책, 라이선스, 품질, 조인, Gold 선택

2) Silver 정규화

순서규칙동작
1읽기 형식지정 컬럼을 문자열로 읽어 앞자리 0 보존
2결측 토큰'-', 'N/A' 등의 값을 결측으로 처리 (전역·컬럼별 지정)
3컬럼 병합명칭만 다른 복수 컬럼을 단일 컬럼으로 병합. 값 불일치 시 실패
4이름 변경원본 필드명을 표준 명칭으로 변경
5자리 채움지정 자릿수까지 좌측 0 채움
6형 변환bool·date·datetime·float·int·str, 천 단위 쉼표 숫자. 값 손실 시 오류
7파생 컬럼연·월·일 컬럼 기반 날짜 생성, 복수 컬럼 기반 조인 키 생성
  • 선언한 규칙에 한해 위 순서로 적용 (미선언 변환은 미수행)
  • 처리는 DuckDB SQL로 수행, 결과는 Parquet으로 저장

3) 품질 검사

규칙검사 내용
required_column · dtype필수 컬럼 존재, 컬럼 자료형 일치
max_duplicate_rate중복 행 비율 상한
max_null_ratio컬럼별 결측 비율 상한
min_rows최소 행 수
range숫자 컬럼의 값 범위 (경계 포함)
compare_columns두 컬럼의 대소·동일 관계
  • 결과는 pass·warn·fail. fail 발생 시 해당 소스를 Gold 진입 전 중단, warn은 기록 후 진행
  • 미평가 규칙은 통과로 간주하지 않고 결과에서 제외

4) 개인정보 검사와 마스킹

  • 검사 대상: 주민등록번호(날짜·검증 숫자 확인), 전화번호, 이메일, 사업자등록번호, 개인정보 관련 컬럼명
  • 정책: block은 검출 시 중단, warn은 기록 후 진행, allow는 통과 (게시와 병행 불가)
  • 마스킹: 선언 컬럼의 문자열은 [masked], 그 외 자료형은 결측으로 치환
  • 게시는 block 정책으로 개인정보 검사를 통과한 실행에 한해 허용 (다중 사용자 배포 기준)

5) 분할

  • 비율 분할: 시드와 행 순번의 해시로 정렬 후 비율에 따라 분할. 동일 입력에 대해 동일 결과 보장
  • 키 분할: 지정 컬럼의 값별로 분할

6) 테이블 스냅샷과 동시 갱신 제어

  • 상태가 ok인 실행의 Gold만 스냅샷으로 커밋
  • 실행 시작 시점의 테이블 revision을 확보하여 커밋 시 비교. 불일치 시 커밋 거부 및 사유 기록
  • 거부 사유: 동일 이름 테이블 존재, 0행 결과, revision 충돌, 커밋 오류
  • 이전 스냅샷은 최근 3개까지 보관. 저장된 분석이 참조 중인 스냅샷은 정리 대상에서 제외

7) 읽기 전용 SQL 검사

  • sqlglot 구문 분석을 통해 SELECT 단일 문장만 허용 (DDL·DML, 재귀 CTE 불가)
  • 테이블 함수, VALUES·UNNEST·LATERAL, 표본 추출 불가
  • 환경 조회 함수 44종, 비결정 함수 18종 불가
  • 실제 테이블 참조는 논리 이름 dataset 1개만 허용
  • 통과한 문장은 표준형으로 재생성하여 실행. 잠금 설정된 DuckDB 연결과 별도 프로세스로 추가 방어

8) 비동기 실행과 취소

  • 실행은 대기열 등록 후 작업자가 처리. 기본값: 동시 실행 2건, 대기 10건, 실행 시간 6시간
  • 취소는 단계 경계에서만 반영하는 협력적 방식. 기생성 산출물은 부분 Manifest와 함께 보존
  • 소스는 스레드 풀로 최대 4개 병렬 처리, 결과는 명세 순서대로 병합

9) AI 도우미 응답 검증

  • 프롬프트를 고정 지시, 비신뢰 근거, 사용자 질문으로 구분하여 전달
  • 전송 전 키·토큰 명칭의 필드, key=value 형태, 무작위성이 높은 장문 문자열을 자리표시자로 치환
  • ① 구조 검증(Zod) → ② 근거 대조 → ③ Builder 검증 → ④ 사용자 승인
  • 허용 동작 6종만 제안 가능. 실행 시작, 게시, 자격 증명 변경, SQL 자동 실행은 불가
  • LLM 키는 사용자 직접 입력 방식, 기본 메모리 보관

10) 인증과 통신

  • 로그인: Keycloak 기반 OIDC (Authorization Code + PKCE). 토큰은 메모리에만 보관
  • 401 응답 시 토큰 갱신 후 동일 요청 1회 재전송, 실패 시 로그인 화면 이동
  • API 호출: 30초 제한, 연결 실패·시간 초과·5xx에 대해 최대 2회 재시도 (미리보기·제출·게시·쿼리는 재시도 제외)
  • 전체 응답을 Zod 스키마로 검증, 계약 불일치 시 오류 처리
  • Builder 계약 버전이 최소 요건(1.96.0) 미만인 경우 전 화면 경고 배너 표시
  • 제공 기관 키는 Builder에 암호화 저장(단일 사용자) 또는 세션 중 메모리 보관(다중 사용자)

11) 데모 모드와 다국어

  • 기능별 Builder용·데모용 클라이언트 구성, 동일 계약 테스트로 검증
  • Builder 없이 고정 데이터로 전체 화면 확인 가능, 전 화면 Demo 배지 표시
  • 한국어(기본)와 영어 지원

3. 프로젝트 추진 과정에서의 문제점 및 해결방안

1) 프로젝트 관리 측면

  • 일정·협업에서 겪은 문제와 해결 과정 기재

2) 프로젝트 개발 측면

  • 대용량 데이터 처리 한계
    • (문제) 약 1.4GB 파일 소스의 빌드가 실패 (945MB는 성공)
    • (원인) 업로드 본문 전체를 일괄 처리하고, 수집·정제·패키징·내보내기·질의 5개 지점에서 전체 데이터를 메모리에 적재하는 구조
    • (해결) 표 처리 엔진을 Polars에서 DuckDB로 전환하고 단계 간 전달을 Parquet 파일로 변경. 전환 과정에서 두 엔진의 결과 비교 테스트로 동등성 확인
    • (결과) 실행 엔진 코드의 Polars 의존성 제거. 기존 게시 스크립트만 이전 엔진을 유지하며 순차 이전 진행 중
  • 실패한 실행의 상태 표시
    • (문제) 대기 중 취소 또는 서버 재시작으로 종료된 실행의 기록 누락, 테이블 커밋에 실패한 실행이 재시작 후 성공으로 표시
    • (원인) Manifest 생성 전 종료된 실행은 기록 대상에서 누락되었고, 상태 판정 로직이 여러 위치에 분산
    • (해결) 종료 기록을 별도 보관하고, 실행 결과(ok)와 API 작업 상태(succeeded)의 판정을 단일 함수로 통합. 테이블 커밋 실패 실행은 failed로 표시
    • (결과) 전체 실행에 대해 단일 상태 보장, 인덱스 재구성 시에도 동일 결과 유지
  • 테이블 동시 갱신
    • (문제) 동일 테이블에 대한 2개 실행의 동시 갱신 시 후행 결과가 선행 결과를 덮어쓸 가능성
    • (원인) 커밋 시점에 타 실행의 커밋 여부 미확인
    • (해결) 실행 시작 시점의 테이블 revision을 확보하여 커밋 시 비교, 불일치 시 거부. 커밋은 전체 소스 종료 후 단일 스레드에서 수행
    • (결과) 충돌 실행은 conflict 사유를 Manifest에 기록하고 API에서 failed로 표시, 기존 스냅샷 유지
  • AI 답변의 신뢰성
    • (문제) LLM이 존재하지 않는 테이블·실행을 근거로 답변하거나 실행 불가능한 SQL을 제안할 가능성
    • (원인) LLM 출력은 형식·내용 모두 보장 불가
    • (해결) 응답을 구조 검증, 근거 대조, Builder 검증, 사용자 승인의 4단계로 처리. 근거 미확인 항목은 해당 항목만 제거
    • (결과) SQL·명세 변경은 사용자 승인 후에만 실행, SQL은 Builder의 읽기 전용 검사 재수행
  • 화면 구조와 용어
    • (문제) 초기 메뉴가 Discover, Add Data, Builds 등 실행 엔진의 용어 중심으로 구성
    • (원인) 화면 명칭이 빌드, 데이터셋, provider 등 Builder 내부 개념을 그대로 사용
    • (해결) 카탈로그 → 테이블 → 분석 → 운영 순으로 메뉴 재구성, 테이블 만들기를 메뉴가 아닌 화면 내 동작으로 전환하여 3단계로 축소. 이전 주소는 신규 주소로 자동 이동
    • (결과) 이전 화면 명칭이 문구에 재사용될 경우 CI가 실패하도록 검사 추가
  • 화면에 보이는 값의 정확성
    • (문제) Builder 미제공 값을 0 또는 임의 점수로 표시할 경우 실제 상태로 오인할 가능성
    • (원인) 이전 홈 화면은 지표 카드 4종 중심이었으나 일부 지표는 Builder 미제공 값
    • (해결) 홈 화면의 지표 카드를 제거하고 조치 필요 테이블을 우선 표시. 품질은 점수 대신 검사 결과만 표시, 미수신 값은 '확인 불가'로 표기
    • (결과) 전체 표시 값을 Builder 응답 기반으로 구성, 응답 형식의 계약 불일치 시 오류 처리

Ⅳ. 기대효과 및 활용분야

1. 프로젝트의 기대효과

1) 데이터 이용자

  • 기관별 상이한 형식을 표준 테이블로 변환하는 반복 작업 감소
  • 가공 과정이 명세·실행 기록으로 보존되어 동일 결과 재현 가능
  • 코드 작성 없이 화면에서 테이블 생성·SQL 분석 가능

2) 데이터 품질과 신뢰

  • 품질·개인정보·라이선스 점검의 실행 과정 내재화로 배포 전 점검 누락 방지
  • 게시 데이터셋에 출처, 처리 내역, 스키마를 카드 형태로 함께 제공
  • 스냅샷 기반 입력 고정으로 분석 결과 검증 가능

3) 운영과 확장

  • 별도 DB 서버 없이 SQLite·파일 기반으로 동작하여 설치·운영 부담 경감
  • 내보내기 형식·게시 대상을 플러그인 방식으로 확장 가능
  • 공개 저장소 제공으로 자유로운 활용·확장 가능

2. 프로젝트의 활용분야

분야활용 방법예시
교육공공데이터 기반 수업 자료와 실습용 테이블 구축지역별 인구·교통 데이터로 SQL 실습
연구출처와 처리 내역이 기록된 연구용 데이터셋 구축부동산 실거래 매매·전월세 통합 테이블
데이터 분석주기적으로 갱신되는 테이블과 리포트 작성기상 예보, 관광 정보의 정기 갱신
AI 개발학습용 데이터셋 구축과 허브 배포분할(train·valid·test)과 카드가 포함된 데이터셋을 Hugging Face에 게시
