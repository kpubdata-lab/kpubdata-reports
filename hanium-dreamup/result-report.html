Ⅰ. 프로젝트 개요

1. 프로젝트 소개

1) 프로젝트 정의

  • 공공데이터를 분석 가능한 테이블로 만들고 그 과정을 확인하는 플랫폼
  • 사용자가 규칙을 선언하면 수집, 정제, 검증, 패키징, 기록까지 자동으로 수행
  • 만들어진 테이블은 스냅샷으로 보관되어 SQL 분석, 리포트, 내보내기, 게시에 사용
  • 기획 의도: 공공데이터를 '받아오는 일'과 '쓸 수 있게 만드는 일' 사이의 간격을 줄이는 것

2) 구성 요소

구성 요소형태역할
KPubData BuilderPython 패키지, HTTP 서비스, CLI명세 검증, Bronze·Silver·Gold 실행, 테이블 스냅샷과 Manifest 기록, 읽기 전용 SQL, 내보내기와 게시
KPubData StudioReact 웹 애플리케이션카탈로그 탐색, 테이블 만들기, 테이블 조회, SQL 분석, 리포트, 실행·품질·운영 확인
kpubdataPython 라이브러리제공 기관별 공공 API 호출과 표준 레코드 변환. Builder가 가져다 씀
BuildSpecYAML·JSON 명세소스, 스키마 계약, 품질 기준, 분할, 내보내기를 선언하는 실행 입력
Manifestmanifest.json실행마다 남는 결과 기록: 상태, 출처, 행 수, 품질 결과, 실패 내역
웨어하우스Parquet 스냅샷 + SQLite 카탈로그성공한 실행의 결과를 읽기 전용 스냅샷으로 보관

3) 사용 흐름

  • ① 카탈로그에서 소스 데이터셋을 찾고 '시작'을 누름
  • ② 테이블 만들기 마법사에서 파라미터와 규칙을 입력
  • ③ 미리보기로 스키마와 샘플을 확인하고 검증을 통과하면 '만들기' 실행
  • ④ Builder가 수집부터 스냅샷 커밋까지 수행하는 동안 실행 상세에서 진행 상황 확인
  • ⑤ 테이블 상세에서 스키마·품질 확인, SQL 작업 공간에서 분석, 리포트 작성
  • ⑥ 필요하면 파일로 내보내거나 Hugging Face에 게시

4) 주요 용어

용어뜻
소스 데이터셋제공 기관이 공개한 원천 데이터. 카탈로그에서 찾음
테이블소스 데이터셋으로 만든 결과물. 스냅샷의 묶음
스냅샷한 번의 실행이 커밋한 읽기 전용 결과. 테이블마다 최근 3개 보관
실행BuildSpec 하나를 처리한 한 번의 작업. run_id로 구분
Bronze원천 레코드를 그대로 보존한 단계
Silver선언한 규칙으로 정규화하고 검증한 단계
Gold컬럼 선택·마스킹·분할을 거친 최종 단계

2. 개발 배경 및 필요성

1) 공공데이터 활용 환경

  • 생성형 AI 확산으로 출처와 품질이 확인된 학습·분석용 데이터 수요 증가
  • AI 학습 데이터 시장은 2024년 약 26억 달러에서 2030년 86억 달러로 성장 전망 (Grand View Research, 2025)
  • 국내 공공데이터는 OECD 공공데이터 평가에서 4회 연속 1위. 개방 규모는 크지만 가공은 이용자 몫

2) 기존 방식의 문제

구분문제
형식 차이기관마다 응답 형식(XML·JSON), 페이지 처리, 인증 방식, 컬럼 이름이 달라 소스마다 수집 코드를 새로 작성
정제 반복결측 표기('-', 'N/A'), 숫자의 쉼표, 앞자리 0이 잘린 코드 같은 문제를 매번 손으로 정리
이력 부재어떤 입력과 규칙으로 결과가 만들어졌는지 남지 않아 같은 결과를 다시 만들기 어려움
품질 확인중복, 결측, 범위 이탈을 배포 전에 확인하는 절차가 없음
법적 확인개인정보 포함 여부와 재배포 조건을 사람이 따로 확인해야 함
접근 장벽스크립트와 명령줄 중심이라 개발자가 아니면 쓰기 어려움

3) 개발 목표

  • 수집부터 배포까지의 규칙을 하나의 명세로 선언하고, 실행 전에 검증
  • 단계마다 결과를 파일로 남겨 어디서 문제가 생겼는지 확인 가능하게 함
  • 품질·개인정보·라이선스 확인을 실행 경로에 포함
  • 같은 기능을 웹 화면에서 코드 없이 사용
  • 결과 테이블을 스냅샷으로 보관해 분석을 다시 실행해도 같은 입력을 읽게 함

3. 프로젝트 특·장점

1) 기존 방식과의 비교

구분기존 방식본 프로젝트
공공데이터 포털원천 API 제공까지. 가공은 이용자 몫정제·검증·분할·문서화를 거친 테이블과 데이터셋 산출
범용 ETL 도구
(Airflow 등)		파이프라인은 실행되나 검증 규칙은 직접 작성스키마 계약과 품질 기준을 명세에 선언하고 실행 전에 검증
데이터 허브
(Hugging Face 등)		배포·공유 중심. 생성 과정은 남지 않음실행 기록과 입력 지문을 Manifest로 남기고 카드와 함께 게시
LLM 데이터 도구LLM이 내용을 추정해 생성답변을 실제 근거와 대조하고 사용자 승인 전에는 실행하지 않음

2) 기술적 차별점

  • 명세 기반 실행
    • BuildSpec이 실행의 유일한 입력. 화면에서 만든 설정도 같은 명세로 변환되어 전달
    • 실행 전 15개 영역을 검사해 문제를 code·path·message로 한 번에 반환
    • 실행에 쓰인 명세를 스냅샷으로 남겨 나중에 그대로 다시 실행 가능
  • 단계별 결과 보존
    • Bronze·Silver·Gold 결과를 각각 파일로 남겨 단계별로 확인
    • 소스 하나가 실패해도 나머지 소스는 계속 처리하고 실패 단계와 코드를 기록
  • 스냅샷과 재현성
    • 테이블은 읽기 전용 스냅샷으로 커밋. 저장한 분석은 읽은 스냅샷과 함께 보관
    • 입력 지문, 분할 알고리즘, 산출물 다이제스트를 Manifest에 기록
  • 실행 경로에 포함된 점검
    • 품질 검사 7종, 개인정보 패턴 검사와 마스킹, 재배포 조건 판정
    • 게시 전 준비 상태 점검: 라이선스, 개인정보 검사 통과, 카드 항목 누락
  • 역할 분리
    • Studio는 화면, Builder는 검증·실행·질의, kpubdata는 공공 API 접근
    • Studio는 Builder가 주지 않은 값을 만들어 보여 주지 않음 (점수 대신 검사 결과, 못 받은 값은 '확인 불가')
  • 근거에 묶인 AI 도우미
    • 답변의 참조·동작·SQL을 Builder에서 받은 근거와 대조
    • SQL 실행과 명세 변경은 사용자가 승인한 뒤에만 수행

Ⅱ. 프로젝트 내용

1. 프로젝트 구성도

1) 시스템 구성도

  • Studio는 Builder API만 호출하며 실행 엔진을 갖지 않음
  • Builder는 kpubdata로 원천을 받아 Bronze → Silver → Gold 순으로 처리
  • 성공한 실행의 Gold는 테이블 스냅샷으로 커밋되고 실행 내역은 Manifest와 SQLite 인덱스에 기록
  • SQL 질의는 저장된 스냅샷을 읽기 전용으로 조회

2) 서비스 흐름도

  • 미리보기와 검증은 저장 없이 수행. 통과한 뒤에만 실행 제출
  • 실행은 비동기. Studio는 800ms 간격으로 상태를 조회하고 탭이 숨겨지면 조회를 멈춤
  • 작업 상태: queued → running → succeeded · failed · cancelled

3) 데이터 처리 흐름

단계처리산출물
Bronze공공 API·업로드 파일·URL의 원본을 그대로 수집하고 수집 시각·파라미터·건수·체크섬 기록raw_records.jsonl, metadata.json
Silver선언한 규칙으로 정규화, 스키마 검증, 개인정보·품질 검사, 통계와 미리보기 생성table.parquet, schema.json, stats.json, validation.json
Gold행 필터와 컬럼 선택, 개인정보 컬럼 마스킹, 분할, 두 소스 조인table.parquet, package.json, splits/*.parquet
Export지정한 형식으로 내보내고 데이터셋 카드 생성CSV·JSONL·Parquet·Markdown 파일, README.md, card.json
커밋·기록상태가 ok이면 웨어하우스 스냅샷으로 커밋하고 Manifest 기록스냅샷, manifest.json

4) 저장 구조

  • 별도 DB 서버 없이 SQLite와 로컬 파일만 사용
  • 실행 작업공간: {output}/{run_id}/ 아래에 bronze/, silver/, gold/, buildspec.yaml, manifest.json
  • 웨어하우스: {warehouse}/tables/{id}/snapshots/{id}/에 Parquet. 카탈로그는 _warehouse.sqlite
  • 실행 인덱스(_builds.sqlite)는 Manifest에서 다시 만들 수 있는 파생 자료
  • 실행 이벤트, 게시 영수증, 저장된 분석, 명세 개정 이력, 자격 증명(암호화)도 각각 SQLite 파일로 보관

3. 주요 적용 기술

1) 선언형 실행 계약 (BuildSpec)

  • 필수 항목은 dataset_id, title, description, sources 네 가지. 나머지는 필요한 것만 선언
  • 소스마다 스키마 계약(schema)과 Gold 선택(gold)을 따로 지정
  • exports를 비워 두면 테이블 커밋까지만 수행 (내보내기는 선택)
명세 항목선언 내용
sources[]소스 종류(public_api·file·url), 제공 기관·데이터셋, 수집 파라미터, 스키마 계약, Gold 선택
quality중복률·결측률 상한, 최소 행 수, 값 범위, 컬럼 비교와 규칙별 심각도
pii개인정보 검사 정책 (block·warn·allow)
splits분할 방식(ratio·key), 비율, 시드
composition두 소스의 조인 정의 (키, inner·left, 중복·결측 키 처리)
exports[]내보내기 형식과 경로
license 등라이선스, 출처 표기, 게시 여부, 갱신 주기
  • 검증은 실행 자원을 만들기 전에 수행하고 문제를 모두 모아 반환
  • 검사 영역: 필수 항목, 소스 식별, 내보내기, 메타데이터, 분할, 스키마 계약, 소스 종류, 소스 키, 파라미터 축, 개인정보 정책, 라이선스, 품질, 조인, Gold 선택

2) Silver 정규화

순서규칙동작
1읽기 형식지정한 컬럼을 문자열로 읽어 앞자리 0 보존
2결측 토큰'-', 'N/A' 같은 값을 결측으로 처리 (전역, 컬럼별)
3컬럼 병합이름만 다른 여러 컬럼을 하나로 합침. 값이 다르면 실패
4이름 변경원본 필드명을 표준 이름으로 변경
5자리 채움지정한 자릿수까지 왼쪽을 0으로 채움
6형 변환bool·date·datetime·float·int·str, 천 단위 쉼표 숫자. 값이 사라지면 오류
7파생 컬럼연·월·일 컬럼으로 날짜 생성, 여러 컬럼으로 조인 키 생성
  • 선언한 규칙만 위 순서로 적용하고, 선언하지 않은 변환은 하지 않음
  • 처리는 DuckDB SQL로 수행하고 결과는 Parquet으로 저장

3) 품질 검사

규칙검사 내용
required_column · dtype필수 컬럼 존재, 컬럼 자료형 일치
max_duplicate_rate중복 행 비율 상한
max_null_ratio컬럼별 결측 비율 상한
min_rows최소 행 수
range숫자 컬럼의 값 범위 (경계 포함)
compare_columns두 컬럼의 대소·동일 관계
  • 결과는 pass·warn·fail. fail이 있으면 해당 소스를 Gold 전에 중단, warn은 기록하고 진행
  • 평가하지 못한 규칙은 통과로 치지 않고 결과에서 제외

4) 개인정보 검사와 마스킹

  • 검사 대상: 주민등록번호(날짜·검증 숫자 확인), 전화번호, 이메일, 사업자등록번호, 개인정보를 뜻하는 컬럼명
  • 정책: block은 검출 시 중단, warn은 기록 후 진행, allow는 통과 (게시와 함께 쓸 수 없음)
  • 마스킹: 선언한 컬럼의 문자열은 [masked]로, 그 밖의 자료형은 결측으로 변경
  • 게시는 개인정보 검사를 block 정책으로 통과한 실행에만 허용 (다중 사용자 배포 기준)

5) 분할

  • 비율 분할: 시드와 행 순번의 해시로 정렬한 뒤 비율대로 나눔. 같은 입력이면 항상 같은 결과
  • 키 분할: 지정한 컬럼의 값별로 나눔

6) 테이블 스냅샷과 동시 갱신 제어

  • 상태가 ok인 실행의 Gold만 스냅샷으로 커밋
  • 실행 시작 때 테이블의 revision을 기억했다가 커밋할 때 비교. 다르면 커밋을 거부하고 사유 기록
  • 거부 사유: 같은 이름의 테이블 존재, 0행 결과, revision 충돌, 커밋 오류
  • 이전 스냅샷은 최근 3개까지 보관. 저장된 분석이 쓰는 스냅샷은 정리하지 않음

7) 읽기 전용 SQL 검사

  • sqlglot으로 구문을 분석해 SELECT 한 문장만 허용 (DDL·DML, 재귀 CTE 불가)
  • 테이블 함수, VALUES·UNNEST·LATERAL, 표본 추출 불가
  • 환경을 들여다보는 함수 44종, 결과가 매번 달라지는 함수 18종 불가
  • 실제 테이블 참조는 논리 이름 dataset 하나만 허용
  • 통과한 문장은 표준형으로 다시 만들어 실행. 잠긴 DuckDB 연결과 별도 프로세스가 추가 방어

8) 비동기 실행과 취소

  • 실행은 대기열에 넣고 작업자가 처리. 기본 동시 실행 2건, 대기 10건, 실행 시간 6시간
  • 취소는 단계 경계에서만 반영하는 협력적 방식. 이미 만든 산출물은 부분 Manifest와 함께 보존
  • 소스는 스레드 풀로 최대 4개까지 병렬 처리하고 결과는 명세 순서대로 병합

9) AI 도우미 응답 검증

  • 프롬프트를 고정 지시, 신뢰하지 않는 근거, 사용자 질문으로 나누어 전달
  • 전송 전에 키·토큰 이름의 필드, key=value 형태, 무작위성이 높은 긴 문자열을 자리표시자로 치환
  • ① 구조 검증(Zod) → ② 근거 대조 → ③ Builder 검증 → ④ 사용자 승인
  • 허용 동작 6종만 제안 가능. 실행 시작, 게시, 자격 증명 변경, SQL 자동 실행은 불가
  • LLM 키는 사용자가 직접 입력하며 기본적으로 메모리에만 보관

10) 인증과 통신

  • 로그인: Keycloak 기반 OIDC (Authorization Code + PKCE). 토큰은 메모리에만 보관
  • 401 응답 시 토큰을 갱신해 같은 요청을 한 번 다시 보내고, 실패하면 로그인 화면으로 이동
  • API 호출: 30초 제한, 연결 실패·시간 초과·5xx에 최대 2회 재시도. 미리보기·제출·게시·쿼리는 재시도하지 않음
  • 모든 응답을 Zod 스키마로 검증해 계약과 다르면 오류로 처리
  • Builder 계약 버전이 최소 요건(1.96.0)보다 낮으면 모든 화면에 경고 배너 표시
  • 제공 기관 키는 Builder에 암호화해 저장하거나(단일 사용자) 세션 동안만 메모리에 보관(다중 사용자)

11) 데모 모드와 다국어

  • 기능마다 Builder용과 데모용 클라이언트를 두고 같은 계약 테스트로 검증
  • Builder 없이도 고정 데이터로 전체 화면을 확인할 수 있으며 모든 화면에 Demo 배지 표시
  • 한국어(기본)와 영어 지원

3. 프로젝트 추진 과정에서의 문제점 및 해결방안

1) 프로젝트 관리 측면

  • 일정·협업에서 겪은 문제와 해결 과정 기재

2) 프로젝트 개발 측면

  • 대용량 데이터 처리 한계
    • 문제: 약 1.4GB 파일 소스의 빌드가 실패 (945MB는 성공)
    • 원인: 업로드 본문을 통째로 다루고, 수집·정제·패키징·내보내기·질의의 다섯 지점에서 각각 전체 데이터를 메모리에 올리는 구조
    • 해결: 표 처리 엔진을 Polars에서 DuckDB로 바꾸고 단계 사이를 Parquet 파일로 연결. 전환 중에는 두 엔진의 결과를 비교하는 테스트로 동등성 확인
    • 결과: 실행 엔진 코드에서 Polars 의존을 제거. 기존 게시 스크립트만 이전 엔진을 유지하며 순차 이전 중
  • 실패한 실행의 상태 표시
    • 문제: 대기 중 취소되거나 서버 재시작으로 끝난 실행은 기록이 남지 않고, 테이블 커밋에 실패한 실행이 재시작 뒤 성공으로 보임
    • 원인: Manifest가 만들어지기 전에 끝난 실행은 남는 기록이 없고, 상태를 읽는 코드가 여러 곳에 흩어져 있었음
    • 해결: 종료 기록을 따로 남기고, 실행 결과(ok)와 API 작업 상태(succeeded)를 한 함수에서 판정. 테이블 커밋이 실패한 실행은 failed로 표시
    • 결과: 모든 실행이 하나의 상태를 가지며 인덱스를 다시 만들어도 같은 결과가 나옴
  • 테이블 동시 갱신
    • 문제: 같은 테이블을 두 실행이 동시에 갱신하면 나중 결과가 먼저 결과를 덮어쓸 수 있음
    • 원인: 커밋 시점에 다른 실행의 커밋 여부를 확인하지 않음
    • 해결: 실행 시작 때 테이블의 revision을 기억했다가 커밋할 때 비교하고, 다르면 거부. 커밋은 모든 소스가 끝난 뒤 한 스레드에서 수행
    • 결과: 충돌한 실행은 conflict 사유가 Manifest에 남고 API에서 failed로 표시되며 기존 스냅샷이 유지됨
  • AI 답변의 신뢰성
    • 문제: LLM은 존재하지 않는 테이블이나 실행을 근거로 답하거나 실행할 수 없는 SQL을 제안할 수 있음
    • 원인: LLM 출력은 형식과 내용 모두 보장되지 않음
    • 해결: 응답을 구조 검증, 근거 대조, Builder 검증, 사용자 승인의 4단계로 처리. 근거에 없는 항목은 그 항목만 제거
    • 결과: SQL과 명세 변경은 사용자가 승인한 뒤에만 실행되며, SQL은 Builder의 읽기 전용 검사를 다시 거침
  • 화면 구조와 용어
    • 문제: 초기 메뉴가 Discover, Add Data, Builds 등 실행 엔진의 용어 중심으로 나뉘어 있었음
    • 원인: 화면 이름이 빌드, 데이터셋, provider 같은 Builder의 내부 개념을 그대로 따름
    • 해결: 카탈로그 → 테이블 → 분석 → 운영 순으로 메뉴를 다시 묶고, 테이블 만들기를 메뉴가 아닌 동작으로 바꿔 3단계로 줄임. 이전 주소는 새 주소로 자동 이동
    • 결과: 이전 화면 이름이 문구에 다시 들어오면 CI가 실패하도록 검사를 추가
  • 화면에 보이는 값의 정확성
    • 문제: Builder가 주지 않는 값을 0이나 임의 점수로 보여 주면 실제 상태로 오해할 수 있음
    • 원인: 이전 홈은 지표 카드 4종 중심이었는데 그중 일부는 Builder가 제공하지 않는 값이었음
    • 해결: 홈에서 지표 카드를 없애고 조치가 필요한 테이블을 먼저 표시. 품질은 점수 대신 검사 결과만 표시하고 받지 못한 값은 '확인 불가'로 표기
    • 결과: 모든 값이 Builder 응답에서 오며 응답 형식이 계약과 다르면 오류로 처리

Ⅳ. 기대효과 및 활용분야

1. 프로젝트의 기대효과

1) 데이터 이용자

  • 기관마다 다른 형식을 표준 테이블로 맞추는 반복 작업 감소
  • 가공 과정이 명세와 실행 기록으로 남아 누구나 같은 결과를 다시 만들 수 있음
  • 코드를 작성하지 않아도 화면에서 테이블 생성과 SQL 분석 가능

2) 데이터 품질과 신뢰

  • 품질·개인정보·라이선스 확인이 실행 과정에 포함되어 배포 전 점검 누락 방지
  • 게시되는 데이터셋에 출처, 처리 내역, 스키마가 카드로 함께 제공됨
  • 스냅샷으로 분석 시점의 입력이 고정되어 결과를 검증할 수 있음

3) 운영과 확장

  • 별도 DB 서버 없이 SQLite와 파일만으로 동작해 설치와 운영 부담이 작음
  • 내보내기 형식과 게시 대상을 플러그인으로 추가 가능
  • 공개 저장소로 제공되어 누구나 내려받아 사용하고 확장할 수 있음

2. 프로젝트의 활용분야
