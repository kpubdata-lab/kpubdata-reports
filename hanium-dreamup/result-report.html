Ⅰ. 프로젝트 개요

1. 프로젝트 소개

  • 공공데이터를 분석 가능한 테이블로 만들고 그 과정을 확인하는 플랫폼 개발
  • 사용자는 Studio에서 소스 데이터셋을 찾아 테이블 생성 규칙을 입력
  • Builder가 규칙을 검증한 뒤 수집, 단계별 변환, 결과 기록을 수행
  • 만들어진 테이블은 스냅샷으로 보관되어 SQL 분석, 리포트, 내보내기에 사용
  • 주요 결과물: 실행·웨어하우스 엔진 KPubData Builder(Python), 웹 작업공간 KPubData Studio(React·TypeScript), 실행 계약 BuildSpec·Manifest

2. 개발 배경 및 필요성

  • 공공 API 응답을 받은 뒤에도 자료형 정리, 품질 확인, 재실행 기준, 파일 생성 작업이 남음
  • 이 과정을 스크립트와 수작업으로 처리하면 어떤 입력과 규칙으로 결과가 나왔는지 알기 어려움
  • 실행 입력을 BuildSpec으로 선언하고 Bronze·Silver·Gold로 역할을 나누어 결과를 추적할 수 있게 설계
  • 명세 파일과 API만으로는 진입 장벽이 높아, 같은 기능을 화면으로 다룰 수 있도록 Studio 개발

3. 프로젝트 특·장점

구분기존 방식본 프로젝트
공공데이터 포털원천 API 제공까지. 가공은 이용자 몫정제·검증·분할·문서화를 거친 테이블과 데이터셋 산출
범용 ETL 도구파이프라인은 실행되나 검증 규칙은 직접 작성스키마 계약과 품질 기준을 명세에 선언하고 실행 전에 검증
데이터 허브배포·공유 중심. 생성 과정은 남지 않음실행 기록과 입력 지문을 Manifest로 남기고 카드와 함께 게시
LLM 데이터 도구LLM이 내용을 추정해 생성답변을 실제 근거와 대조하고 사용자 승인 전에는 실행하지 않음
  • 책임 분리: Studio는 화면, Builder는 검증·실행·질의, kpubdata는 공공 API 접근 담당
  • 안전 장치: 개인정보 검사, 라이선스 확인, 읽기 전용 SQL 검사를 실행 경로에 포함

Ⅱ. 프로젝트 내용

1. 프로젝트 구성도

  • Studio는 Builder API만 호출하며 실행 엔진을 갖지 않음
  • Builder는 kpubdata로 원천을 받아 Bronze → Silver → Gold 순으로 처리
  • 성공한 실행의 결과는 테이블 스냅샷으로 커밋되고 실행 내역은 Manifest로 기록

3. 주요 적용 기술

  • 선언형 실행 계약 (BuildSpec)
    • 소스, 스키마 계약, 품질 기준, 분할, 내보내기를 하나의 명세로 선언
    • 실행 전에 15개 영역을 검사해 문제를 한 번에 알려 줌
  • Medallion 단계 처리
    • Bronze: 원천 레코드와 수집 시각·파라미터·체크섬 보존
    • Silver: 선언한 규칙만 적용해 정규화하고 스키마·품질·개인정보 검사
    • Gold: 컬럼 선택, 마스킹, 분할, 조인 후 패키징
  • DuckDB·Parquet
    • 표 처리 엔진을 DuckDB 하나로 통일
    • 결과는 Parquet 스냅샷으로 저장하고 격리된 연결에서 읽기 전용으로 질의
  • 실행 기록과 스냅샷
    • 실행마다 Manifest 한 건 기록, SQLite 인덱스로 조회
    • 스냅샷 커밋은 revision 비교로 동시 갱신 충돌 방지
  • 읽기 전용 SQL 검사
    • sqlglot으로 구문을 분석해 단일 SELECT만 허용
    • 테이블 함수, 비결정 함수, 외부 접근 차단
  • AI 응답 검증
    • LLM 답변을 구조 검증 → 근거 대조 → Builder 검증 → 사용자 승인 순으로 확인
    • 전송 전에 키·토큰 등 비밀값 제거
  • 인증
    • Keycloak 기반 OIDC (Authorization Code + PKCE), 토큰은 메모리에만 보관

  • 일정·협업에서 겪은 문제와 해결 과정 기재

2) 프로젝트 개발 측면

  • 대용량 데이터 처리 한계
    • 문제: 수집부터 질의까지 여러 지점에서 전체 데이터를 메모리에 올려, 약 1.4GB 파일 소스의 빌드가 실패
    • 해결: 표 처리 엔진을 Polars에서 DuckDB로 바꾸고 단계 사이를 Parquet 파일로 연결. 기존 게시 스크립트만 이전 엔진 유지
  • 실패한 실행의 상태 표시
    • 문제: Manifest가 만들어지기 전에 끝난 실행은 기록이 없어 화면에서 사라짐
    • 해결: 종료 기록을 따로 남기고, 실행 결과(ok)와 API 작업 상태(succeeded)를 한 함수에서 판정
  • 테이블 동시 갱신
    • 문제: 같은 테이블을 두 실행이 동시에 갱신하면 나중 결과가 먼저 결과를 덮어씀
    • 해결: 시작 시점의 revision을 기억했다가 커밋할 때 비교해 다르면 거부
  • AI 답변의 신뢰성
    • 문제: LLM은 존재하지 않는 테이블이나 실행을 근거로 답할 수 있음
    • 해결: 답변의 참조를 Builder 근거와 대조해 없는 항목을 제거하고, SQL과 동작은 사용자 승인 후에만 실행
  • 화면 구조의 복잡도
    • 문제: 초기 메뉴가 Discover·Add Data·Builds 등 실행 엔진의 용어 중심으로 나뉘어 있었음
    • 해결: 카탈로그 → 테이블 → 분석 → 운영 순으로 메뉴를 다시 묶고, 테이블 만들기를 3단계로 줄임
  • 화면에 보이는 값의 정확성
    • 문제: Builder가 주지 않는 값을 0이나 임의 점수로 보여 주면 오해 소지
    • 해결: 품질은 점수 대신 검사 결과만 표시하고, 받지 못한 값은 '확인 불가'로 표기

4. 프로젝트를 통해 배우거나 느낀 점

  • 팀원별 소감 기재

Ⅳ. 기대효과 및 활용분야

1. 프로젝트의 기대효과

  • 공공데이터 가공 과정을 명세와 실행 기록으로 남겨 누구나 같은 결과를 다시 만들 수 있음
  • 기관마다 다른 형식을 표준 테이블로 맞추는 반복 작업을 줄임
  • 품질·개인정보·라이선스 확인이 실행 과정에 포함되어 배포 전 점검 누락을 방지
  • 코드를 작성하지 않는 사용자도 화면에서 테이블 생성과 SQL 분석 가능
  • 공개 저장소로 제공되어 누구나 내려받아 사용하고 확장할 수 있음

2. 프로젝트의 활용분야

  • 교육·연구: 공공데이터 기반 수업 자료와 연구용 데이터셋 구축
  • 데이터 분석: 주기적으로 갱신되는 테이블 구축과 SQL 분석, 리포트 작성
  • AI 개발: 출처와 처리 내역이 기록된 학습용 데이터셋 구축과 허브 배포
  • 공공·민간 서비스: 공공데이터를 활용하는 서비스의 데이터 준비 단계
