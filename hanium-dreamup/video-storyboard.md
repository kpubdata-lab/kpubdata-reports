# 시연 영상 설계와 콘티

한이음 드림업 공모전 제출 영상(결과보고서 Ⅱ-6 "프로젝트 작동 동영상")의 설계와 콘티입니다.

- 상태: 렌더링 완료(1:28, 1920×1080). 팀 검토 후 유튜브 HD 업로드
- 제한 시간: **1분 30초**. 편집 목표는 **1:28**(2초 여유)
- 참고 형식: CUBRID Lab 소개 영상의 설계 문서([`cubrid-lab/showcase` `projects/cubrid-lab/intro-video/VIDEO_DESIGN.md`](https://github.com/cubrid-lab/showcase/blob/main/projects/cubrid-lab/intro-video/VIDEO_DESIGN.md)). 2초 박자 격자, 샷 단위 콘티, 음절 예산 검사, 정직성 원칙을 같은 방식으로 씁니다.
- 내용 근거: 결과보고서와 근거 목록(`evidence.md`, 2026-10-12 커밋 기준)

## 1. 개념

**한 줄:** *공공데이터를, 바로 쓰는 테이블로.* 명세 하나로 수집부터 게시까지 검증하고 기록하는 플랫폼, KPubData Builder와 Studio.

화면을 차례로 누르는 녹화가 아니라 제품 소개처럼 만듭니다. 바탕은 흰색, 로고와 색은 KPubData Brand v2를 씁니다. 시연 장면은 모두 실제 녹화이고, 창 모형 안에 넣어 중요한 곳만 확대하며, 그 위에 한국어 문구를 먼저 띄웁니다. 컷은 120 BPM 배경음의 마디(2초)에 맞춥니다.

### 기존 영상에서 바꿀 점

기존 영상(「2026 한이음 드림업 공모전 제출 영상 - Kpubdata studio 시연」)은 Studio 화면 녹화 중심입니다.

1. **문제부터**: 기능보다 먼저 "공공데이터를 바로 못 쓰는 이유"를 10초 안에 보여 줌
2. **Builder와 Studio를 나눠 설명**: 화면 뒤에서 실행 엔진이 하는 일을 구성도 한 장으로 연결
3. **한 줄기 시나리오**: 한 사용자가 아파트 실거래가로 테이블을 만들고, 분석하고, 게시하는 흐름 하나
4. **문구 먼저, 증거는 화면으로**: 장점 문구가 0.3~0.5초 먼저 뜨고, 그것을 증명하는 화면이 뒤따름
5. **말은 줄이고 화면이 설명**: 내레이션은 샷 길이의 75~90%만 채우고 나머지는 음악과 숨 쉴 틈으로 남김

### 보는 사람

1. 공모전 심사위원: 1분 30초 안에 "무엇을 해결했고, 실제로 동작하는가"를 판단
2. 결과보고서를 함께 읽는 사람: 보고서의 기능과 차별점이 실제 화면으로 이어지는지 확인

### 전달 순서

1. **공공데이터는 바로 쓰기 어렵다**: 형식 차이, 정제 반복, 이력 부재
2. **명세 하나로 검증하고 기록한다**: BuildSpec → Builder 실행 → Manifest
3. **코드 없이 웹에서 끝까지**: 찾기 → 만들기 → 확인 → 분석 → 게시
4. **믿을 수 있다**: 실행 전 검증, 단계별 결과, 읽기 전용 스냅샷, 승인 후에만 실행하는 AI

화면 문구(실제 영상): "형식은 제각각, 정리는 손으로.", "명세 하나로, 기록까지.", "실행 전에, 먼저 검증.", "원본은 그대로, 정제는 규칙대로.", "같은 스냅샷, 같은 결과.", "AI는 제안, 실행은 사용자."

### 넣지 않는 것

품질 센터, 모니터링, 연결·설정, 리포트 작성, 검증 실패 예시, 개발 환경과 테스트, 문제 해결 과정. 시장 규모·OECD 순위는 원문 확인 전이라 쓰지 않습니다.

## 4. 화면 설계

### 4.1 색과 글꼴

영상 전체를 **흰 바탕**으로 깔끔하게 만들고, 로고와 색은 KPubData Brand v2를 따릅니다. 기준은 kpubdata-studio의 `docs/brand/VISUAL_IDENTITY.md`와 `assets/logo/kpubdata-brand-assets/`입니다. Studio 화면과 영상이 같은 브랜드로 보이게 하려는 것입니다.

| 쓰임 | 값 | Brand v2 이름 |
|---|---|---|
| 바탕 | `#FFFFFF` | Surface |
| 카드·창 모형 테두리 | `#E5E7E2` | Border |
| 제목, 본문, 화면 문구 | `#172033` | Ink |
| 보조 문구, 구간 표시(01·02…), suffix | `#64748B` | Slate |
| 강조 밑줄, 확대 상자, 선택 표시 | `#2563EB` | Brand Blue |
| 데이터 흐름 선, 차트 강조 | `#06B6D4` | Data Cyan |
| 작은 데이터 장식(점, 보조 선) | `#14B8A6` | Fresh Mint |
| 문제 표시(Q1) | `#B91C1C` | 상태 색 Failure |
| 통과 표시(D3, R2) | `#15803D` | 상태 색 Success |

- **로고**: K 심볼(`video/symbol_light.svg`, kpubdata-studio `fe5b774`에서 복사)을 고치지 않고 씁니다. 회전, 그림자, 그라데이션, 빛 번짐, 3D를 넣지 않고, 심볼 높이의 ½만큼 사방을 비웁니다.
- **이름**: `KPubData`가 주인공이고 `Builder` · `Studio`는 더 작고 Slate색입니다. suffix에 Blue·Cyan·Mint를 쓰지 않습니다.
- **색의 양**: 화면 대부분은 흰색과 Ink입니다. Blue·Cyan·Mint로 넓은 면을 채우지 않습니다. Mint를 "성공" 의미로 쓰지 않고, 통과·실패는 상태 색과 글자로 보여 줍니다.
- **B2 그림**: 결과보고서 그림의 Bronze·Silver·Gold 색 대신, 흰 카드 + Border 테두리 + Ink 글자로 그리고 단계 사이 흐름만 Data Cyan 선으로 잇습니다.

글꼴은 Pretendard(문구·자막, `video/PretendardVariable.woff2`, SIL OFL 1.1), JetBrains Mono(SQL, BuildSpec). 제목 88 px / 800, 화면 문구 68~104 px, 본문 34 px, 코드 25 px 이상. 아래쪽 150 px는 자막 자리로 비워 둡니다. 시안 파일은 `video/title-card.html`이고, `video/frames/T1.png`는 Chrome으로 찍은 것입니다.

```sh
cd hanium-dreamup/video
google-chrome --headless=new --hide-scrollbars --window-size=1920,1080 --screenshot=frames/T1.png "file://$PWD/title-card.html"
```

### 4.2 움직임 원칙

- **음악이 박자를 정함**: 120 BPM. 컷과 문구 등장은 박자 위, 구간 시작(01·02·03·04 표시)은 마디 첫 박
- **문구 먼저, 증거 다음**: 문구가 0.3~0.5초 먼저 나오고 그 다음 화면이 들어옴
- **녹화는 덧칠하지 않음**: 창 모형, 2.5배 이하 확대, 확대 상자와 밑줄만 얹음. 2배 넘게 빨리 돌린 구간은 "×N" 표시
- **한 번에 하나만 움직임**: 흔들림, 글리치, 번쩍임 없음

## 5. 소리

### 5.1 내레이션

- 계획 속도는 샷 길이 1초에 4.5음절입니다. 보통 한국어 낭독 속도(초당 5~6음절)보다 느리게 잡아, 음악과 숨 쉴 틈을 남깁니다. 전체 약 310음절입니다.
- `video_narration_budget.py`가 영어 이름을 읽는 소리로 바꿔(`Builder` → 빌더, `SQL` → 에스큐엘, …) 샷마다 음절을 세고, 예산을 넘거나 전체 길이가 1:24~1:30을 벗어나면 실패합니다.

  ```sh
  python3 hanium-dreamup/video_narration_budget.py
  ```

- 목소리로 팀원을 알아볼 수 있어 TTS를 씁니다. CUBRID Lab 영상의 시연판과 같은 Supertonic 3(로컬 CPU 실행)의 `M5` 음성, 속도 1.0입니다. 엔드 카드와 영상 설명에 AI 음성임을 적습니다.
- 내레이션 문장과 읽는 소리는 [`video/voice/lines.json`](video/voice/lines.json)에 있습니다. 영어 이름은 한글로 적어 읽힙니다. KPubData는 **케이퍼브데이터**로 읽습니다. "케이펍데이터"는 음성 인식(faster-whisper small)이 네 음성 모두 "K-POP 데이터"로 알아들어서 바꿨습니다.
- 합성한 15줄은 음성 인식으로 다시 받아 적어 확인했고, 줄마다 샷 길이 안에 들어갑니다(가장 긴 A2 6.6초 / 샷 8초).

### 5.2 자막

내레이션 전체를 한국어 자막으로 넣습니다(최대 2줄, 한 줄 18자 안팎, 한 자막 1초 이상, 구 단위로 끊음). 심사 화면에서 소리 없이 재생될 수 있으니 자막은 영상에 입힙니다.

### 5.3 배경음

[`video/music/generate.py`](video/music/generate.py)가 numpy로 120 BPM 배경음을 직접 합성합니다(C–G–Am–F 패드, 8분음표 아르페지오, 약한 킥, 시드 26). 샘플·루프·녹음·AI 음악 서비스를 쓰지 않아 Content ID 문제가 없습니다. 시연 구간(0:28~1:20)은 아르페지오와 킥이 조금 촘촘해집니다. 내레이션이 나올 때 배경음은 약 10 dB 낮추고(0.5 → 0.16), 최종 파일은 −14 LUFS, 최대 피크 −1 dBTP로 맞춥니다.

## 6. 녹화 사양

녹화는 [`video/rec/`](video/rec/)의 Playwright 스크립트로 합니다. 다시 찍어도 같은 동작이 나옵니다.

- **화면**: Xvfb 가상 화면(2880×1800)에 Google Chrome을 키오스크 모드로 띄우고, 1440×900 CSS 픽셀·배율 2로 그립니다. ffmpeg x11grab으로 30 fps 녹화합니다. 영상에서 2배까지 확대해도 선명합니다.
- **커서**: Playwright 입력은 X 포인터를 움직이지 않아서 페이지 안에 커서와 클릭 표시를 그립니다(`lib.cjs`).
- **글꼴**: 녹화 머신(리눅스)에는 한글 시스템 글꼴이 없어 Studio가 WenQuanYi로 그려집니다. 녹화 브라우저에서만 Studio의 시스템 글꼴 자리(`--font-sans`)에 Pretendard를 지정합니다. 화면 내용과 동작은 바꾸지 않습니다.
- **Builder**: [`serve-builder.sh`](video/rec/serve-builder.sh)가 빈 작업 디렉터리로 단일 사용자 개발 모드(인증 생략)를 띄웁니다. 게시 전 개인정보 검사 필수(`KPUBDATA_BUILDER_REQUIRE_PII_SCAN_FOR_PUBLISH=true`)를 켭니다. 공공데이터포털 키(`KPUBDATA_DATAGO_API_KEY`)와 게시 준비 점검용 `HF_TOKEN`은 환경변수로 줍니다. 실거래가 API는 XML 응답이라 Builder 환경에 `xmltodict`(kpubdata `xml` extra)와 `huggingface-hub`(게시 준비 점검)가 있어야 합니다.
- **Studio**: 실제 연동(5199 → Builder 8010)과 데모 모드(5198, G1만) 두 개를 띄웁니다.
- **명세**: [`apt-trade-gangnam.yaml`](video/rec/apt-trade-gangnam.yaml). 서울 강남구(11680) 2024년 9월 거래분 224건입니다. 조회 조건은 화면에서 입력합니다. 정규화 규칙, 품질 규칙(필수 컬럼·최소 행 수·중복률·결측률·값 범위), 개인정보 `block`, 라이선스(공공누리 1유형), 내보내기(parquet·huggingface)는 촬영하지 않는 구간에 위저드의 YAML 편집 모드로 적용합니다.

| 녹화 | 동작 | 길이 | 쓰는 샷 |
|---|---|---|---|
| rec-01-catalog | 카탈로그 "아파트" 검색 → 시작 | 7초 | D1 |
| rec-02-configure | 조회 조건 입력(이후 YAML 적용은 녹화하지 않음) | 10초 | D2 |
| rec-03-preview-run | 미리보기·검증 → 검토 → 테이블 만들기 → 실행 상세 완료·품질 | 21초 | D2, D3, R1, R2 |
| rec-04-table | 테이블 상세 → 스냅샷 탭 | 6초 | A1 |
| rec-05-sql | 스냅샷 선택 → SQL 입력 → 실행하고 저장 → 차트로 보기 | 23초 | A2 |
| rec-06-publish | 게시 준비 상태 → 데이터 카드 | 8초 | G2 |
| rec-07-assistant | 데모 모드 Ask KPubData 질문 → 근거·제안 → 승인 | 16초 | G1 |

```sh
# Studio 두 개를 띄운 뒤(record-all.sh 머리말 참고)
BUILDER_DIR=~/GitHub/kpubdata-builder STUDIO_DIR=~/GitHub/kpubdata-studio \
  bash hanium-dreamup/video/rec/record-all.sh /path/to/rec
```

녹화 중 확인한 것:

- 처음 명세에서는 개인정보 `block` 정책이 실제로 빌드를 막았습니다. 컬럼명 규칙(`NM`·`NAME` 포함)이 `aptNm`, `roadNm` 같은 원천 컬럼을 개인정보 의심 컬럼으로 잡았습니다. 값이 아니라 컬럼 이름 때문이라 해당 컬럼의 이름을 바꿔(`apartment`, `road` 등) 통과시켰습니다.
- Studio 위저드는 YAML에 `metadata` 키가 없거나 소스 `schema`에 `required`·`dtypes`가 없으면 적용하지 못합니다(`src/features/add-data/model.ts`의 `applyBuildSpecToDraft`가 `spec.metadata.outputPath`를 읽다가 멈춤). 명세에 빈 값을 넣어 피했습니다.

## 7. 원칙

### 7.1 익명 원칙

팀원을 짐작할 수 있는 정보는 영상 어디에도 넣지 않습니다(학교 정보 포함).

| 넣지 않는 것 | 나올 수 있는 곳 | 처리 |
|---|---|---|
| 이름, 팀명, 과제 번호 | 엔드 카드, 화면 문구, 자막 | 쓰지 않음 |
| 학교·학과, 학교 로고·교표 | 엔드 카드, 배경, 바탕화면, 브라우저 탭 | 쓰지 않음, 녹화 전 탭·바탕화면 정리 |
| 개인 이메일, 학교 메일(`ac.kr`) | 로그인 화면, 사용자 메뉴, 관리 화면, 자격 증명 | 시연용 계정 사용 |
| GitHub·Hugging Face 계정명, 조직 주소 | 엔드 카드, 게시 위치, 커밋 작성자 | 시연용 계정·조직 사용, GitHub 주소는 넣지 않음 |
| 컴퓨터 사용자명, 홈 경로 | 파일 업로드 창, 터미널, 브라우저 주소창(`file://`) | 시연용 OS 계정 또는 녹화 영역에서 제외 |
| 목소리, 얼굴 | 내레이션, 웹캠 | TTS 사용, 웹캠 없음 |
| 학교·지역을 드러내는 데이터 | SQL 결과, 조회 조건 | 특정 학교·캠퍼스를 고르지 않음(구 단위 집계는 그대로) |

- 기존 영상은 개인 이름의 유튜브 채널에 올라가 있습니다. 새 영상은 공모전 안내에 따라 제출하고, 유튜브에 올려야 하면 개인 이름이 드러나지 않는 채널에 "일부 공개"로 올립니다. 영상 제목·설명에도 이름과 학교를 쓰지 않습니다.
- 영상 파일의 메타데이터(작성자, 제목)를 내보내기 전에 지웁니다. 예: `ffmpeg -i in.mp4 -map_metadata -1 -c copy out.mp4`
- 최종 점검에서 영상 전체를 0.5배속으로 한 번 보며 위 표의 항목이 없는지 확인합니다.

### 7.2 정직성 원칙

1. 시연 샷은 모두 실제 녹화입니다. 결과 값을 고치거나 합성하지 않습니다. 빨리 돌린 구간은 표시합니다.
2. 데모 모드로 찍은 샷은 G1 하나입니다. 녹화 머신에 LLM API 키가 없어서입니다. Studio가 응답에 표시하는 "DEMO · mock 데이터"를 가리지 않고, 화면 위에 "데모 모드 · mock 데이터" 표시를 따로 붙입니다. 나머지 샷은 모두 실제 Builder와 공공데이터포털 API로 찍었습니다.
3. 게시는 준비 상태 점검과 데이터 카드까지만 보여 주고 게시 버튼은 누르지 않습니다. 내레이션도 "게시할 수 있습니다"로 말합니다.
4. 촬영하지 않은 구간(YAML 적용)은 콘티와 녹화 사양에 적어 둡니다.
5. 성능 수치는 쓰지 않습니다. 결과보고서에 측정 근거가 없습니다.
6. [8. 사실 근거](#8-사실-근거)에 없는 주장은 하지 않습니다.
